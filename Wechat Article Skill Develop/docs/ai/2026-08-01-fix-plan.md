# 修复计划：wechat-article-subscriber 可交付性修复

> 计划来源：会话 `019fbd0e-8d40-7052-b981-22a5acc560cd` 代码审查发现的问题。
> 目标：让项目达到可发布交付标准。本计划只做修复，不引入新功能、不重写架构。
> 生成日期：2026-08-01

## 0. 背景与基线

上轮审查结论：OpenClaw/Hermes 平台支持已清除，但项目仍有 3 个 P1 逻辑缺陷和 2 个 P2 交付问题，未达到可发布标准。

本次规划前实测基线（2026-08-01，隔离环境 `/tmp/was-venv`）：

- 全量测试：`148 passed, 3 skipped`（跳过项均为 Windows 专用）。
- 发布校验：失败，`skill bundle contains unexpected top-level paths: ['.DS_Store']`。
- 源码打包：产出 `wechat-article-subscriber-1.0.0-github-source.zip`，版本取自 plugin.json（1.0.0），与 CHANGELOG（2.1.0）不一致。
- 工作区有上轮未提交改动（README、config_store.py、manage.py、test_management.py、references/feishu.md，及 3 个已删除的 dist 2.1.0 产物），本计划必须在其之上继续，不得覆盖或回退。

已复现的缺陷机制：

- **P1-1 并发保存复活授权**：`load_config() → 修改 → save_config()` 无锁；两个进程并发时，先失效授权的进程的保存会被后保存的旧副本覆盖，授权重新生效（已用脚本复现）。
- **P1-2 done/dismiss 竞态**：`complete_article` 在文章已被 `dismiss_article` 处理后仍返回该「已撤回」条目（metadata 只有 disposition，无评分），`cmd_done` 随后会把它同步到飞书且缺少完整评分数据（已用脚本复现）。
- **P1-3 Base 创建半途失败不可恢复**：远端 Base 已创建并保存 `base_token/table_id`（enabled=False, provisioning="created"）后，若授权经理授予或字段检查失败，重试被「a Feishu target is already configured」守卫阻断，没有续跑路径。

### Step 1：P1-1 授权边界与并发保存

#### 1a. 扩展授权范围字段

- **结果**：任何改变「授权实际覆盖范围」的飞书字段变化都会失效已确认授权。
- **修改范围**：`execution_policy.py` 的 `FEISHU_APPROVAL_SCOPE_FIELDS` 增加：
  `binding_mode`、`agent_source`、`expected_user_open_id`、`cli_profile`、`field_mapping`（保留现有 7 个字段）。
- **理由**：这些字段决定同步写入的目标表/字段和身份（哪个 App、哪种绑定、哪个用户）；任一变化都超出原授权。`field_mapping` 由 `manage feishu-check --save-mapping` 和 init_config 补丁写入，现有逻辑不会失效授权。
- **前置**：无（独立函数，不影响调用方）。
- **验收标准**：对新增的每个字段单独变化，`feishu_approval_scope_changed` 返回 True；无关字段变化仍返回 False。
- **验证**：新增单元测试 `test_scope_field_changes_invalidate_policy`（遍历新增字段）。运行 `pytest tests/test_management.py -k policy`。
- **失败回退**：仅改常量与测试，`git restore` 单文件即可。
- **注意（用户可感知行为变化）**：字段映射刷新后将要求重新确认执行政策，这是本次修复的预期安全行为，交付时需向用户说明。

#### 1b. 配置并发写保护

- **结果**：任意两个进程并发读改写配置时，后写者不再用旧副本覆盖已失效的授权或丢失并发修改。
- **修改范围**：
  - `config_store.py`：新增 `config_lock()`（复用 `queue_lock` 的 fcntl/msvcrt + 超时模式，锁文件 `data_dir()/config.lock`）；新增 `modify_config(mutator: Callable[[dict], dict]) -> dict`，签名语义为「持锁 load → mutator 就地修改 → validate → save → 返回保存后的配置」。
  - 将全部「`load_config()` 后修改再 `save_config()`」的读改写路径迁移到 `modify_config`，包括：`config_store.update_health`；`manage.py` 的 `_feishu_destination`、`_import_feishu_host_context`、`_feishu_identity`、`_feishu_app`、`_feishu_manager`、execution-policy 确认、`feishu-disable`、reset 中涉及 policy/feishu 的写路径；`init_config.py` 各 section 保存；`process_pending.py` 的 `cmd_feishu_check --save-mapping` 与订阅添加；`discover_only.py` 两处。
  - `_feishu_create_base` 尾部三次 `save_config`（先存禁用态、再启用、再存映射）合并为一次 `modify_config` 事务（见 Step 3）。
  - 保留 `save_config` 供「从零构建全新配置」的路径（如 `config_from_agent_payload`、重置命令），这些路径不携带旧状态，无覆盖风险。
- **完整性检查**：迁移后 `rg -n "save_config\\("` 剩余调用点应只剩两类：全新配置构建、`modify_config` 内部保存。
- **前置**：Step 1a（无强依赖，可并行，但同一 PR 内完成更易回归）。
- **验收标准**：
  1. 复现脚本（两进程场景）改为通过 `modify_config` 提交后，后写者基于最新配置执行，授权失效结果不被覆盖。
  2. 所有管理命令行为不变（全量回归通过）。
- **验证**：
  - 新增 `test_concurrent_stale_save_does_not_resurrect_policy`：A 通过 `modify_config` 失效授权并保存后，B 的陈旧 mutator 提交不会复活授权。
  - 新增 `test_update_health_does_not_clobber_policy_change`：并发 `update_health` 与授权失效，最终授权仍为失效态。
  - 全量 `pytest -q`。
- **失败回退**：若迁移导致既有命令失败，`git restore` 涉及的 5 个脚本文件，保留 1a 的常量与测试即可独立恢复。

### Step 2：P1-2 done/dismiss 并发竞态

- **结果**：已撤回（dismissed）的文章不会被 `done` 完成或同步到飞书；对已撤回文章执行 `done` 返回清晰错误而非静默成功/错误数据。
- **修改范围**：
  - `queue_helpers.complete_article`：当待处理队列中找不到文章、但 `processed` 中存在 `metadata.disposition == "dismissed"` 的条目时，抛 `LookupError`（消息说明文章已撤回，不能完成），不再返回该条目。仅在条目是正常完成记录时返回幂等结果。
  - `process_pending.cmd_done`：捕获 `complete_article` 抛出的 `LookupError`，输出干净的错误（human/JSON 两种格式，沿用现有 `failure()` 包装），返回 1；任何路径都不得对 dismissed 条目调用 `_sync_entry`。
  - 防御性校验：`cmd_done` 在同步前检查返回条目的 `metadata.disposition`，若为 dismissed 直接失败。
- **前置**：Step 0。
- **验收标准**：
  1. 复现脚本（dismiss 后 complete_article）改为抛错；队列保持 dismissed 条目不变。
  2. 带 `--feishu` 的 `done` 对已撤回文章返回非零退出码、不调用飞书写入（mock `upsert_article` 断言未调用）。
  3. 正常完成、dismiss/restore、失败同步留待重试等既有行为不变。
- **验证**：
  - 新增 `test_complete_after_dismiss_raises`（tests/test_core.py）。
  - 新增 `test_cmd_done_after_dismiss_does_not_sync`（tests/test_management.py，mock 飞书 upsert）。
  - 运行 `pytest tests/test_core.py tests/test_management.py -q` 及全量回归。
- **失败回退**：单文件回退（queue_helpers.py / process_pending.py），不影响其他步骤。

### Step 3：P1-3 Base 创建部分成功后恢复

- **结果**：远端 Base 已创建但后续步骤（经理授予、字段检查）失败时，重试同一命令可从中断处续跑，不再被「目标已存在」阻断，也不会重复创建远端 Base。
- **修改范围**：`manage.py` 的 `_feishu_create_base`：
  - 修改「target already configured」守卫：仅当 `provisioning != "created"` 时拒绝；当 `destination == "create"` 且 `provisioning == "created"` 且 `base_token/table_id` 均已保存时，跳过 `create_standard_base`，直接使用已保存标识符进入后续步骤。
  - 后续步骤保持幂等：`grant_bot_created_resource` 重复授予安全（实现时确认 lark-cli 行为，若重复授予会报错则捕获并视为成功）；`preflight_feishu` 只读；字段映射与启用为覆盖写。
  - 将尾部三次 `save_config` 合并进 Step 1b 的 `modify_config` 事务，确保中间状态（enabled=False, provisioning="created"）始终可恢复。
  - 失败时保持中间状态可续跑：授权/预检失败时异常上抛，但已保存的 `provisioning="created"` 状态不被清除。
- **前置**：Step 1b（尾部保存并入事务）。
- **验收标准**：

- **验证**：新增 `test_feishu_create_base_resumes_after_grant_failure`、`test_feishu_create_base_still_refuses_foreign_target`（tests/test_management.py，mock bitable_client 边界）；运行 `pytest tests/test_management.py -k create_base` 与全量回归。

## 4. 风险与未决项

- **行为变化（预期）**：字段映射、绑定方式、App/用户标识变化后需重新确认执行政策；`done` 对已撤回文章由「静默返回」变为「明确报错」。均属本次修复目标，但需在交付时向用户说明。
- **残余限制**：远端 Base 创建成功但本地保存失败的极端窗口（CLI 成功与 config 保存之间崩溃）仍无法恢复，需人工用远端资源名找回；本计划不处理，记录为已知限制。
- **残余风险**：Step 1b 迁移涉及 20+ 个写路径，回归面较大，因此要求全量回归 + 定向并发测试；若迁移过程中发现某命令语义依赖旧的非事务行为，返回本计划重新确认，不擅自保留半锁状态。
- **未执行验证**：Windows、真实网络、GitHub Actions。

## 5. 需用户决定的事项

- **D1 版本方向**：推荐 plugin.json 升到 2.1.0（与 CHANGELOG 及上轮删除的 2.1.0 产物一致）；备选是把 CHANGELOG 头改回 1.0.0。选择影响发布产物命名。
- **D2 仓库结构方案**：推荐「仓库根加 CI 工作流 + 根 README 指针，项目保持嵌套」（改动最小，不影响打包工具路径）；备选「把项目整体上移为仓库根」（结构更干净，但会改变全部打包/测试/适配器相对路径，改动大）。
- **D3 授权失效范围扩大**：推荐采纳（安全默认）；若业务上希望「仅刷新字段映射不要求重新确认」，需单独说明理由并缩小范围。

计划确认后按 `engineering-loop` 执行；任一决策点未确认前，对应步骤（Step 4 版本、Step 5 结构）先不落地。
